# 判断准则（change-watch）

拿到 `out/latest.json` 里的变更集后，**逐条**按下述准则判断。这套准则是判断的唯一依据；
要改判断口味，改这里，不要改脚本。

## 一、四条必答问题

对每一条变更，依次回答：

1. **是真的变更吗？** —— 不真的（营销稿、传闻、只发预告、例行小版本）就判为无关。
   **判为无关也要写出来**：在 judged.json 里给那条写 `"discard": true` 加一句 `discard_reason`，
   脚本会核销它并记进 `log/discarded.jsonl`。**什么都不写 = 漏判**，它会被反复带回重问，
   直到给出判断；超过 24 小时仍未判才记进 `log/unjudged.jsonl`。
   **"判不出来" ≠ "判为无关"**：材料不足时写
   `significance: "unknown"`，它会落盘（不丢）但**一定不通知**（没判断过就不许发）。
2. **属于什么类型？** —— 自己命名，用最短的中文短语（见 §三 参考表，可自拟新类型）。
3. **有多重要？** —— `high` / `normal` / `low` / `unknown`（见 §四）。
4. **要不要通知？** —— 写进 `notify` 字段。**默认 `high`/`normal`/`low` 都通知**（实时性：变更不拖延，全级别照常发）；`unknown` 仍强制不通知（没判断过就不许发）。要把某条主动抑制成「落盘但不发」时，显式写 `notify: false`（例如你判断它是真变更但属于噪声）。`log_change.py` **只把 `notify: true` 的条目放进通知卡片**。

**铁律：凡是要发出去的通知，都必须先答完这四个问题。** 不允许把 `out/latest.json` 里的原文
直接转发。

**每条判断都要原样带回 `change_id`**（`latest.json` 里每条变更自带，形如 `a1b2c3d4e5f6`）。
脚本靠它核对"是不是每条都判了"——**漏答一条 = 这次判断不完整**，会点名告诉你，并把那条留在待判
队列里，下一轮 `watch.py` 再问一次——按**未判年龄**过期（默认 24 小时），而非按采集轮次，
所以采集再频繁也不会把未判的变更提前吃掉；超时才记进 `log/unjudged.jsonl`。
**漏答不是"判断为无关"，是失败。**

## 二、什么不算变更（防假条款）

命中任一条 → **判为无关**（写 `discard: true` + 一句理由，记进 `log/discarded.jsonl`），不进变更流水：

- **营销稿 / 品牌宣传**：没有新产品、新能力、新价格，只有"我们很厉害"。
- **传闻 / 二手转述**：没有官方来源（如只有媒体"据称"）。
- **"即将推出"却没有日期**：只有预告，没有可验证的事实。
- **例行小版本**：补丁、修 bug、地区补齐、平台上架，能力没变。
- **同一事件的多家转载**：只记一条。
- **页面上的噪声变化**：推荐位轮换、阅读量、更新时间戳刷新、导航改版。
  （若某源的变更几乎全是这类，说明配置的源选错了，应调整配置而不是放宽准则。）

## 三、类型参考表（建议，不强制）

| 类型 | 含义 | 例子 |
|---|---|---|
| `模型发布` | 新模型/新版本上线 | 出现一行新 Model ID |
| `模型下架` | 对象从清单里消失 | 某 Model ID 不再出现在清单 |
| `计划下线` | 官方给出未来下线日期 | `Retirement date` 出现或前移 |
| `能力变化` | 已有对象的能力/规格变化 | 上下文长度、模态、速率限制 |
| `价格变化` | 定价变动 | 每百万 token 单价改动 |
| `更名` | 对象改名或换代 | `Replacement model ID` 指向新名字 |
| `新产品线` | 出现全新品类 | 新的 Agent 框架、新的开发工具 |
| `政策/条款` | 使用政策、可用地区、合规变化 | 地区支持范围调整 |
| `其他` | 以上都不像 | 自行补一个更准确的名字 |

自拟新类型时：**两到六个汉字**，能被复用到下一次，不要写成一句话。

## 四、重要性分档

| 档 | 判据（满足任一即可） | 默认动作 |
|---|---|---|
| `high` | ① 影响"现在还能不能用"（下架/计划下线/更名/价格）；② 新模型或新版本首次上线；③ 能力出现代际变化 | **通知** |
| `normal` | 已有对象的能力小幅变化、新文档/新教程、新地区开放 | **通知** |
| `low` | 例行维护、表述调整、无实质影响 | **通知（次要）** |
| `unknown` | 材料不足、判不出来（缺原文 / 只有标题 / 页面读不出内容） | 落盘，**不通知** |

**`low` ≠ 噪声**：`low` 是真·小变更（例行维护、表述微调、无实质影响），照常通知；只有判为「非真变更」才走 `discard`（见 §二）。二者不要混淆——`discard` 是完全不进流水，`low` 是进流水且通知（只是级别低）。

**下架类一律 `high`** —— 这是本技能存在的主要理由之一，不要降级。
**`unknown` 绝不许通知** —— 它由脚本强制，改不了。宁可少发一条，也不发没判断过的东西。

## 五、多来源同事件

同一条事实被多个源报道时：

- 合并成**一条记录**。
- **被合并掉的那几条，把它们的 `change_id` 写进 `merged_change_ids` 数组**（见 §七）。
  不写的话，覆盖度校验会以为你漏判了它们——**合并不是漏判，但要显式说出来**。
- `sources` 列出所有能点开的原文链接，**并给每个链接一个中文名** —— 官方一手排最前。
  写成对象数组最准；只给 URL 时脚本会拿配置里的源名去猜（猜不中就退化成域名，很难看）。
- `summary` 里写清"另有 N 家来源报道"。
- 只通知一次。

## 六、时间口径

- 官方源的时间戳不一定可信：同一篇公告，`blog.google` 与 `cloud.google.com` 的自报时间实测可相差约 7 小时。
- 记录变更时，**每个来源各记各的时间**；不要为了"统一"而只留一个。
- 判断"新不新"以**本技能的采集时刻**为准，不以信源自报时间为准。

## 七、写出去的字段

每条判断产出一个对象，交给 `scripts/log_change.py`：

```json
{
  "change_id": "a1b2c3d4e5f6",
  "target": "google",
  "change_kind": "added",
  "type": "模型发布",
  "significance": "high",
  "object": "gemini-3.5-flash",
  "title": "Google 发布 Gemini 3.5 Flash",
  "summary": "一句话说清变了什么、影响谁（答案先行，不抄原文）。",
  "url": "https://…",
  "sources": [
    {"name": "Google 官方博客 · Gemini", "url": "https://…"},
    {"name": "Google Cloud 新闻稿", "url": "https://…"}
  ],
  "notify": true,
  "notify_reason": "为何值得看：…",
  "merged_change_ids": ["b1c2d3e4f5a6"]
}
```

硬性要求：

- **`change_id` 原样复制**，不要改、不要省略。
- `merged_change_ids` 可选：把本次被合并进来的其他变更的 `change_id` 列出来（多来源同事件时用）。
- `title` 里的公司名、产品名，**必须在该条变更的原文里出现过** —— 不许推断。
- `summary` 一句话，回答"变了什么 / 影响谁"，不写形容词堆砌。
- `summary` / `title` 里出现的**版本号、日期、价格必须能在原文里找到**。脚本会逐个核对，
  对不上的标 `grounding: "unverified"` 并在输出里点名——看到这条提示就回原文改，别放着不管。
- `url` 必须能点开原文；拿不到就说明判断依据不足，回到第 1 问重判（或判 `unknown`）。
- `sources` 给中文名（对象数组形式）。

### 落盘之后：卡片由脚本生成，不要手拼

`log_change.py` 落盘后会**直接产出可发送的飞书卡片** `out/card-<时间>.json`（标题、中文标签、
来源名、末尾统计全部已在代码里写好）。**直接发这份 JSON。**

这里有过一次真实事故：手拼卡片时把机器值 `normal` / `low` 原样发了出去，读者还得猜英文含义。
所以补一条硬规则：**卡片这件事不要在脚本之外重做一遍。** 确需手改，也必须遵守
`references/notify-card.md` 的翻译表与自检清单。
