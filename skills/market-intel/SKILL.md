# market-intel（市场情报雷达）

把行业情报**持续抓到、判断过、沉淀下来**，并把潜在客户**按规则筛出来、带着证据推出去**。通知统一走**飞书**。

**分工（沿用 change-watch 的核心设计）**

| 谁 | 做什么 | 为什么 |
|---|---|---|
| **脚本**（确定性） | 采集、差分、企业档案聚合、规则求值、落盘、产卡 | 可复现、不花钱、可无人值守、可回测 |
| **模型（你）** | 读变更集 → 判断情报价值 / 抽取企业事实 → 写 judged.json → 发送卡片 | 这是判断，不是查表 |

**只有变化进判断，不是全量。** 每轮跑完先看 `out/latest.json`，里面只有变化。

## 心智模型：一条流水线，四层

```text
公共源登记册(sources.json) → 采集适配器(rss/mp_account/web_page)
  → 事件差分(latest.json) → AI 判断(judged.json：情报记录 + 企业事实)
  → 企业档案(facts/*.json) → 规则匹配(rules.json：scope + signal_groups)
  → 线索(log/leads.jsonl) → 飞书卡片(群简报 / 私信线索 / 高分群@)
```

与既有技能的关系：**借鉴 change-watch 的工程模式，不共享代码**——差分/待判队列/健康三态/卡片纪律
与其语义一致（运维心智不换），数据模型与采集器按市场情报需求全新设计；企业归一与信源分级沿用
AIHOT 的词表与 tier 概念。**字段与结构能继承的一律继承，不另造一套。**

## 工作区

默认 `~/.market-intel/`（`--workspace` 可换）。首次运行 `pipeline.py --init` 会把
`config/*.example` 复制进去，**此后改工作区那份**：

| 路径 | 内容 |
|---|---|
| `sources.json` | 公共源登记册（两个需求共用，`serves` 标记 intel/lead）。RSSHub 类源用 `rsshub://路由` 写法，部署地址统一在 `settings.rsshub_base` 一处改；已核实渠道清单、部署与排错见 `references/rsshub-sources.md` |
| `entities.json` | 企业与行业词表（entity 归一依据，沿用 AIHOT 词表思路） |
| `rules.json` | 线索规则（三层模型，改规则不改代码） |
| `notify.json` | 通知目标（飞书 user_id/chat_id/mention）+ 猎隼池写入预设（bitable，已实装） |
| `state/streams/*.json` | 上一轮快照（差分对照物） |
| `state/health.json` | 源健康三态（ok/flapping/down） |
| `state/pending.json` | 待判队列：本轮待判断的变更，判完核销 |
| `out/latest.json` | 本轮变更集，**先看这个** |
| `out/leads-latest.json` | 本轮新线索 |
| `out/card-*.json` | 可直接发送的飞书卡片（**不要手拼**） |
| `facts/<entity_id>.json` | 企业档案（融资事件 / 招聘信号 / 行业标签） |
| `log/intel.jsonl` | 已判断的情报流水 |
| `log/leads.jsonl` | 线索流水（字段与多维表格预设一一对应） |
| `log/discarded.jsonl` / `unjudged.jsonl` / `rolled_out.jsonl` / `runs.jsonl` | 丢弃留痕 / 超时未判 / 窗口滚动 / 每轮小结 |

## 工作流

### 用户触发的标准流程（"跑一下"、"看看有什么新东西" → 按此执行，唯一入口）

人工触发时**必须按下列顺序逐条执行**，不得即兴增减步骤（历史上行为不稳定的根源就是
缺这个顶层入口，AI 自行拼流程）：

1. **采集**：`pipeline.py --run`。退出码 1=配置错（明确报告，不静默）；2=有源失败
   （继续，但要在最终汇报里点名）；3=锁冲突（本轮跳过，不重试）。
2. **判空**：读 `out/latest.json` 的 `summary.needs_judgment`（旧版用 `len(changes)`）。待判为 0 且无失败 →
   回报"本轮无新增"，**不发卡**（无增量不发卡，也不发空卡占位）。
3. **判断**：按 `references/intel-criteria.md` + `lead-criteria.md` 对每条 change 给结论
   （弃权也要写 `discard: true` + 理由）；有融资/招聘等事实的抽 facts。
   **必须先过第 3.5 步的硬口径**（黑名单/轮次/双轨/销售指引），它是判定的前置闸门，
   不是参考资料——先按口径筛掉不做的，再逐条写结论。
4. **落盘**：`judge.py --input judged.json --dry-run` 预检 → 通过后去掉 `--dry-run` 正式执行。
   🔴 CHECKPOINT：预检不过禁止落盘。
   **复用历史判定时必须带两个防重/防漏参数**（不传会误判，2026-10-27 实测两次踩坑）：
   ```bash
   # 全量复判（重置/拷贝历史登记）：防旧闻重发
   judge.py --input judged.json --already-sent <备份>/log/intel.jsonl
   # 增量轮（上轮有落盘未发的内容）：再补锚点，防漏发
   judge.py --input judged.json --already-sent log/intel.jsonl \
            --sent-before "<当前 digest_anchor 的 anchor 值>"
   ```
   - `--already-sent`：登记里有的 change_id 一律压成 notify=false（防重发）
   - `--sent-before <锚点>`：**只有真正随内参发出过的才算已发**——`logged_at >= 锚点`
     的 notify=true 记录是"判定过但没发出"，必须保留 notify=true 继续进卡（防漏发）
   - **不确定某条是否发过时，用 `logged_at` 与锚点比较判断**，不要凭"登记里有"就
     认定已发——那正是 2026-10-27 两次误判的根源（一次把已发当未发差点重复轰炸，
     一次把未发当已发造成漏发）
5. **问头图**（人工触发必做）：按「内参头图自定义」段询问是否更换活动图片；
   用户给了就 `--hero-image <值>`，不给用默认图。
6. **产卡**：`judge.py --digest` 产内参卡（用户要头图时带 `--hero-image`）。
7. **AI 内容核查（发送前必做，2026-10-27 用户明令）**：产卡后、**发预览之前**，
   先把卡的实际渲染文本抽出来逐项过一遍——不是看 JSON 结构，是**逐条读内容像不像人看的**：
   - **旧闻检查**：是否混入已通报过的内容（`logs/intel.jsonl` 里 `suppressed_by_guard=true` 的标题）；
   - **判定质量检查**：标题是否有研报/通稿套话（"分析师强call"、"某公司"、"值得关注"），
     `low` 级条目是否违规进了重点新闻段（陷阱 44）；摘要是否与标题不符；
   - **空段/骨架检查**：有没有标题极短、无摘要、无来源的空条目；有没有整段 0 条却留标题；
   - **数字核查**：摘要里的金额/比例/时间是否与原文一致（grounding 只查"原文有没有这些数字"，
     **不查语义对不对**，语义要人/AI 读）；
   - **版式检查**：活动段场次是否与情报重复、榜单段是否误收非榜单条目。
   发现问题 → **就地修正 judged 数据并重产卡**（不是发了再补），修正后重新核查。
   🛑 STOP：AI 核查不通过禁止进入第 8 步（发预览）。
8. **私信预览**：按 `notify.user_id` 发本人私信，同时会话内给出**核查结论摘要**
   （过了哪几项、有无可疑项）。
   🛑 STOP：**等本人确认**。未确认不发群、不推锚点。
9. **按配置发送 + 推锚**：确认后按 `notify.chat_id` 发群 → 成功后 `--digest --commit`。
   发送失败的处置：不 commit（宁重勿漏），落盘 `notify-unsent-*.md` 并明确告知。
10. **线索入池（特批豁免，与发卡无关）**：本轮有新线索 → 调研补全 14 字段
   （`--research-check` 审计）→ `--bitable --commit` **直接写入，不询问**（去重不重复建行）
   → 汇报"已写入 N 条 + 表格链接"。**默认不发线索卡**（见发送纪律）。

**关键边界**：第 10 步与第 7–9 步是**两条互不阻塞的线**——入池该做就做，不需要等卡确认；
但也**不得因为入池就额外发线索卡**（发卡是展示类，受第 6 步纪律约束）。

### 第 0 步：初始化

```bash
python3 <技能目录>/scripts/pipeline.py --init
```

复制配置模板并列出待办（飞书 ID 怎么查、哪些源还没启用）。**推送目标由 AI 协助确认后写回**
（连接器 / `lark-cli im +chat-search --query 群名`），脚本不强制绑定通道。

### 第 1 步：建基线（不推送）

```bash
python3 <技能目录>/scripts/pipeline.py --baseline
```

快照当前全部条目。**这一轮不产出变更、不通知**——否则把历史当新消息推。

### 第 2 步：常规一轮

```bash
python3 <技能目录>/scripts/pipeline.py --run     # 退出码: 0 正常 / 1 配置错 / 2 有源失败 / 3 锁冲突
```

产出 `out/latest.json`。`summary.needs_judgment == 0` 且无失败/停更 → 本轮干净，结束；
待判数量大于 0（包括 `pending_carried`）→ 进入第 3 步。失败与停更已由脚本维护（`summary.sources_down` / `stale_sources`），不用你算。

### 第 3 步：AI 判断（你来做）

读 `out/latest.json` 的 `changes`，对**每一条**给出结论，写成一个 `judged.json`：

```json
{

     "url": "原文链接", "sources": [{"name": "量子位", "url": "…"}],
     "notify": true, "notify_reason": "为何值得看",
     "number_notes": {"300": "300亿美元 = 原文 $30B 单位换算"}},
    {"change_id": "…", "type": "活动情报", "significance": "normal",

                  "signup_url": "…"},

  ]

```

判断准则见 `references/intel-criteria.md`（情报双轨 + 销售指引）、
`references/lead-criteria.md`（事实抽取、八行业口径、kinds 约定、防张冠李戴）与
`references/activities-criteria.md`（活动情报白名单/黑名单）。三条铁律沿用 change-watch：

- **漏答一条 = 判断不完整**：每个 `change_id` 必须被 intel（含 discard / merged）或
  facts.change_ids 覆盖，`judge.py` 会核对，缺一条点名退出码 2；
- **判不出来写 `significance: "unknown"`**：落盘但不通知（脚本强制）；
- **不真的写 `discard: true` + 一句理由**：留痕，不悄悄消失。

> 上面 facts 示例用「橘猫宇宙」（虚构的早期轮次小公司）而不用真实大厂：
> 示例即规范，照抄示例里的公司名会直接把巨头写进线索（2026-10-27 黑名单落地前，
> 示例用的是月之暗面，正是被用户点名"人尽皆知的大巨头"）。判定前先看第 3.5 步 A 条。

### 第 3.5 步：潜客与资讯的硬口径（2026-10-27 用户实地反馈整改，最高优先级）

> 用户原话："推给我的潜客线索严重过时且缺乏价值：你总是在给我推希音（SHEIN）、
> 钛动、声网这类人尽皆知的大巨头或出海成熟服务商……推这些大厂对我来说纯属噪音。"

**A. 潜客线索：坚决剔除巨头，专盯「腰部黑马」**

1. **绝对负向黑名单（脚本硬拦截，不靠提示词）**：`<工作区>/denylist.json` 维护三类
   禁推名单——超级巨头与独角兽、成熟出海服务商与友商、已上市或 C 轮及以上融资。
   **命中即硬丢弃**：不落 `leads.jsonl`、不进线索池、不上报。
   **默认就有保护，不需要你先配**（2026-10-27 用户注）：`config/denylist.json.example`
   就是内置默认底座（117 巨头 / 49 服务商 / 12 禁轮次），三层语义——
   - 工作区**没有** `denylist.json` → 直接用内置默认（开箱即过滤）；
   - 工作区有文件但**某维度为空**（`{"version":1}` / `deny_entities: []`）→ 该维度
     自动并入内置默认（避免"配了文件却零过滤"，那正是用户抱怨的场景复现）；
   - 用户**给了内容** → 完全用用户的，不掺默认。
   要真正清空（不推荐）显式写 `"use_builtin_default": false`。
   **名单只在配置文件里改**，**不要改代码或本文档**；
   完整名单与口径见 `denylist.json` 与 `references/lead-criteria.md`「黑名单与轮次」段。
2. **目标客群锁定**：只做天使轮 / Pre-A / A / B 轮的成长型出海团队。融资类规则组
   已加 `round_any` 白名单（`rules.json`），C 轮及以上不命中任何组。
3. **重点抓的三类外显信号**（这三类是本技能独有的，细则只在本文档）：
   - 在 Google Play / App Store **海外特定国家或小语种市场**（拉美/中东/东南亚/日韩）
     排名蹿升的**中国开发者账号**（榜单源差分 + 新晋判定）；
   - 在 Meta / Google Ads / TikTok **低调但大规模买量起量**的出海短剧、独立站、
     泛娱乐应用、AI 工具（用「招聘海外广告优化师/UA 岗位」等**可得的间接信号**佐证；
     **不要去挖投放金额**——公开渠道拿不到，见下方 C 条）；
   - **大厂核心技术/业务高管离职创办**、且海外已有产品上线的新实体（人事变动 + 新产品双信号）。
4. **明确不做**：不推常识性大厂动态当线索、不推生态伙伴、不推晚期融资。

**B. 资讯拆双轨，只抓公开硬事实** —— **判定细则以 `references/intel-criteria.md` 为唯一真源**
（轨道定义、盯防清单、`sales_playbook`/`sales_strategy` 写法与正反范例都在那里）。
此处只记三条不可协商的裁决点：

- `type` 只取 `技术战报` / `战略风向` 两个值（分别对应"竞对与价格战" / "格局与红利转移"）；
- 两类 notify=true 时**必须**分别带 `sales_playbook` / `sales_strategy`，**≥40 字且
  必须落到具体能力/行业/方案**，写「更稳定更安全」「值得关注」这类空话一样拒；
  **缺则 `judge.py` 拒落盘 exit 2**（代码强制，不是建议）；
- **降价/调价/高性价比新模型 = 最高优先级**，必须第一时间推。

**C. 明确「不采集」的信号（写进规范，别再浪费时间瞎猜）**

以下公开渠道根本拿不到，判定时**不要试图挖、不要编、不要写进卡片**：
`内部算力配额`、`私下大客户折扣`、`未公开商务条款`、`非公开投放金额`。
用户原话："不要试图去挖那些公开网络根本扒不到的……这些不现实。"
替代做法：用**可得的间接信号**推断（招聘 UA/增长岗位 ≈ 在买量；榜单蹿升 ≈ 起量；
官网新增多语言/多区域 ≈ 出海扩张），并在 `summary` 里说明是间接推断。

**D. 国内模型专项源（已配置，实测可用）**

`deepseek-news`（rsshub://deepseek/news）与 `qwen-blog`（rsshub://qwen/blog）已加入
`sources.json`，`serves=intel`、`tier=T1`。火山引擎/MiniMax/Kimi/智谱暂无可用
RSSHub 路由（实测 404），靠综合科技媒体 + `entities.json` 词表覆盖。



**数字 grounding 三层判定**（防止说明里出现原文没有的数字）：① 直接出现在原文 → 通过；
② 常见换算（`$30B`→300亿美元、30,000 人→3 万人、×7.2 汇率等）→ 脚本自动兜底通过并留档；
③ 兜底认不出的换算 → AI 在 `number_notes` 里申报依据后通过（备注留档供人工审计）；
三层都不满足 → 标 `unverified` 并告警。**申报必须属实**——`number_notes` 是留痕通道，
不是洗白虚构数字的通道。

### 第 4 步：落盘、匹配、产卡

🔴 CHECKPOINT（落盘前必做）：首次判定或复用判定组装后，先加 `--dry-run` 在沙箱
临时副本上预检（真实工作区零写入），报错当场修正重跑，**预检通过才执行本步**。

```bash
python3 <技能目录>/scripts/judge.py --input judged.json
```

脚本依次：覆盖度校验 → 情报流水落盘（grounding 数字核对）→ 企业事实并入档案
（web_page 招聘关键词确定性直录）→ 规则匹配出线索（scope 三维硬筛 + 组间 OR；
任一 tier=P0 组命中 → P0 线索实时通知，仅 P1 组命中 → 入池进日报不实时打扰）→ 产出卡片：

| 卡片 | 内容与作用 | 何时出现 | 发给谁 |
|---|---|---|---|

| `card-intel-<时间>-group.json` | 情报卡群@版（红头 + 首行 @）——同上按需 | 用户明确要求且含 high | 群 @ |
| `card-leads-<时间>.json` | **线索卡（按需点播，默认不发）**：本轮新产 P0/P1 线索，含画像/机会点/「查看线索」直达猎隼池记录。**入池本身是特批自动的，但发这张卡不是** | 用户明确要求"看线索"/"发线索卡" | 本人私信 |

| `card-status-<时间>.json` | **状态卡**：源失败/异常需知会——系统健康告知 | 管线检测到异常 | 本人私信 |

**发送纪律（行为边界）**：

**总则：动作分两类，不得混用（2026-10-27 用户明令，最高优先级）**

| 类别 | 包含什么 | 纪律 |
|---|---|---|
| **业务动作类** | `--bitable --commit` 写入猎隼线索池 | **特批豁免预览断点**：命中即写（14 必研字段齐备即写）、去重不重复建行、写完给链接；人工**事后**表内核查修正 |
| **展示类（一切发卡）** | 内参卡、情报卡、线索卡、群@版、状态卡 | **一律按本纪律**：默认只发内参卡，其余不发（见下条） |

- **默认只发一张内参卡，其余卡一律不发（用户明令，防消息轰炸）**：除非用户**明确要求**
  （"逐条推"、"单独发群"、"发线索卡给我看"），否则任何场景（人工触发 / 定时巡检）
  **只产出并发送「市场团队内参：近期热点与活动简报」这一张**。情报卡、线索卡、
  状态卡、群@版**默认不发送**——它们的内容已内嵌在内参卡四段里，单独再发即为轰炸。
  判断口诀：**用户没点名要某张卡，就只有内参卡**。
- **发预览前必须先做 AI 内容核查（2026-10-27 用户明令，硬门槛）**：任何卡片
  （用户触发或巡检产出）在**发本人私信预览之前**，必须由 AI 逐项核查实际内容：
  ①旧闻混入 ②判定质量（研报套话/`low` 违规进重点段）③空段骨架 ④数字语义
  ⑤版式正确性。**核查不通过就地修正数据重产卡，不发给用户看废卡**——
  把不合格的卡推给人预览，等于让人替你查错，是流程失效。
  核查项详见工作流第 7 步；无人值守巡检同样要核查（只是不发预览，直接发配置目标）。
- **用户触发先私信预览、确认后再按配置发（2026-10-27 用户明令）**：人工触发（"跑一下"、
  "看看有什么新东西"、交互调整版式/文案）产出的内参卡，**AI 核查通过后**按
  `notify.user_id` 发本人私信预览——飞书卡片组件（@行/头图/按钮）在 AI 会话内
  无法保真渲染，会话内只能给结构化摘要作辅助，**实卡以私信为准**；
  本人确认后才按 `notify.chat_id` 发群。
  交互调整场景下每轮修改后都重新核查 + 重新私信预览，直到确认。
  **无人值守的定时巡检不受预览断点约束**（没有人可确认），但**AI 内容核查照做**，
  核查通过后直接按配置发送。
- **情报卡（card-intel）与群@版是按需点播卡**：仅当用户明确要求"逐条实时推"、"单独推
  这条到群"时才发；平时情报内容随内参大卡的「行业重点新闻」段带出。
- **卡片超 30KB 会自动分片，分片必须全部发（2026-10-27 实测，v0.6.6）**：
  飞书硬上限 = **请求体 30KB**（错误码 230025）**且元素/组件 ≤ 200**（错误码 300305）。
  `write_card` 已内置护栏（`split_card`），超限自动切多张、标题带 `（1/3）` 标记、
  stderr 打印 `[card-size] ... 已自动切成 N 张`。
  **纪律**：分片属**同一张逻辑卡**，不违反"只发一张"——判断口诀是
  **"一次产出的全部片 = 一张卡"**，必须**按片序全部发完**才算发出。
  **只发第一片 = 丢掉后面所有情报**，且因锚点随后推进而永久丢失（比超限报错更隐蔽）。
  同理 `--digest --commit` 会先落 `state/digest_pending_send.json` 待发送清单
  （含全部片路径与覆盖的 change_id）；发送失败时**凭它精确补发**，不要重新跑 `--digest`
  （窗口已推进，重跑拿到的是空卡）。
  为什么必须分片而不是砍内容：实测某轮 29 条通知，销售指引只占卡片体积 23%，
  **全部删掉仍有 30KB**——内容量本身决定了单卡装不下，砍任何一块都不够且违背用户要求。
- **线索卡（card-leads）同样是按需卡**：线索**入池是特批豁免**（自动写、无需确认），
  但**发线索卡属于展示类**——默认不发；用户明确要"看线索"、"发线索卡"时才发。
  P0 线索默认不出群@（改由内参卡的「潜在客户与业务情报」段红标带出）。
- **发送目标以 `~/.market-intel/notify.json` 为唯一配置源**：`notify.user_id`（私信）、
  `notify.chat_id`（群）、`notify.mention`（@ 规则）都在其中；目标或禁发名单变更时
  **只改 notify.json（含注释红线），不改本文档**。发送前必须读当前配置，禁止沿用
  会话记忆或历史记录中的群/人 ID。测试期若有目标限制（如只允许私信+指定测试群、
  禁发某些业务群），以 notify.json 注释中的红线为准——2026-10-26 晚曾因沿袭
  change-watch 旧双群约定把 P0 线索群卡误发进非配置群，教训即：**目标只认配置单源，
  不得从历史会话、旧技能约定或注释里的「待切换」表述推断**。
- **测试卡只发 notify.json 配置的目标群**且头部标注「链路测试」，验证渲染后即弃。

**内参头图自定义（2026-10-27 新增）**：默认头图（indigo 渐变 banner）可替换为用户
提供的活动图片。机制与流程：

- **图片必须先上传飞书换 `image_key`**（卡片不收本地路径/外链 URL）——用户判断正确；
  `lark-cli im images create --as user --data '{"image_type":"message"}' --file <图>`
  （`im:resource` scope，user 身份与发卡身份一致；2026-10-27 实测可用）。
  规范：≤10M、高:宽 ≤16:9；image_key 租户内通用，拿到后可长期复用。
- **输入形态智能识别（不呆板，任意形态兜底）**：`judge.py --digest --hero-image <值>`
  与 `notify.hero_image` 自动识别——① 裸 `img_v…` key 直通；② 飞书图片链接
  （内嵌 key）提取直通；③ http(s) 图片链接下载后上传；④ 本地路径上传；
  ⑤ 混杂文本尽力提取内嵌 key。任何失败明确告警并回退默认图，不阻断产卡。
  同链接/同图双级缓存（`state/hero_images.json`），绝不重复上传。
- **三级优先级**：`--hero-image` > `notify.hero_image` > 代码内置默认图。
- **必须主动提示更换（2026-10-27 用户明确要求）**：**人工触发**产卡时，产卡前
  **必须问一句**：
  > 是否更换活动图片？可直接发①飞书图片链接 ②任意 http(s) 图片链接
  > ③`img_v…` key ④本地图片路径；不换就用默认图。
  
  用户给了就按上面五形态识别上传换 key 再产卡；用户说不用/未给则用默认图直接产卡。
  **无人值守定时巡检不得询问**（无人可答），按 `notify.hero_image` 或内置默认图直接产卡。
- **替换必须预览确认**：属于「用户触发的展示类卡片」——产卡后先发本人私信预览实卡
  （会话内无法保真渲染图片），本人确认后才按配置发群。

**群卡 @ 规则**：`*-group.json` 首元素自动带 @ 提醒行，由 notify.json `notify.mention`
驱动（`"all"` = `<at id=all></at>` @所有人，需群主开"任何人可@所有人"权限；
`["ou_xxx"]` = 只 @ 指定人；空 = 不 @）。群消息**一律 `--as user`**（沿用 change-watch
实测纪律：bot 发群卡 @ 不生效且易被折叠）。当前群目标与切换状态以 notify.json 为准。

**卡片直接发送脚本产出的 JSON，不要手拼**；发送通道优先级（2026-10-27 用户明确）：
**飞书连接器优先 → 本地 lark-cli CLI 备选 → 落盘 `notify-unsent-*.md` + 会话内明确提醒**；
若会话中存在更好用的发送工具（如新的 MCP 发送能力），AI 可自行评估选用——**原则是达到
"卡片保真送达配置目标"这一效果即可，不呆板绑定某一通道**，详见
`references/notify-card.md`。

**发送参数速查（CLI 兜底时照抄，两类身份不可互换）**：

```bash
# 私信（本人预览 / 状态卡）—— bot 身份 + user_id
lark-cli im +messages-send --as bot --user-id <notify.user_id> \
  --msg-type interactive --content - < out/card-daily-XXXX.json

# 群（内参卡 / 按需群@卡）—— 必须 user 身份 + chat_id（bot 发群 @ 不生效）
```

返回 `"ok": true` + `message_id` 即成功；失败按报错处理并落盘 `notify-unsent-*.md`。
**发送后核验**（防误发）：目标群本轮消息数应为预期值，多发了要立即说明。

### 第 5 步：线索入池闭环（自动写入，人工事后核查）

**写入特批自动（2026-10-26 用户拍板，2026-10-27 复核确认）**：调研命中即写，
**不卡「人工确认预览」断点，也不需要用户确认**——新线索 → AI 调研补全（14 必研字段
硬门槛）→ `judge.py --bitable --commit` 一条命令自动写入（先重建预览吸收最新调研再写，
**主名+别名去重，已存在的绝不重复建行**）。写完汇报"已写入 N 条 + 表链接"，
人工**事后**在表格里核查修正。

**注意：入池 ≠ 发卡**。`--lead-card` 产出的线索卡属于**展示类**，默认**不发**；
仅当用户明确要求"看看线索"/"发线索卡"时才发（见「发送纪律」总则）。

安全性依据：写入链路自带五重护栏——调研 14 字段硬门槛（不齐全 blocked 拒写）、
公司名去重（主名 + 别名候选精确检索，exists 不重写、不重复建行）、**exists 通知隔离**
（已在线索池的线索私信卡标注「已存在」、绝不进群 @ 催建联——已存在的公司不是新潜在线索）、
select 选项校验（无效值丢弃留痕）、幂等可重跑（写入 failed 的线索保留待写状态自动重试，
不会一次网络抖动就静默丢单）。

`status`（new/confirmed/rejected）保留为**事后核查字段**：人工在表内/leads.jsonl
复核后改 `confirmed` / `rejected`，`rejected` 的记录是规则调优的依据。
它与 `bitable_status`（pending/pushed/exists/filtered/failed/blocked，脚本回写
写入结果用）是两个字段：写入由 `--bitable --commit` 驱动、选 `bitable_status=pending`
的线索，**不要求先改 `status`**。

**每日摘要（固定时刻，如 08:30）**：跑 `judge.py --digest` 产内参卡 → 按 `notify.chat_id`
发群；**发送成功后**再跑 `judge.py --digest --commit` 推进锚点（宁重勿漏：失败不 commit，
下次自动重覆盖）。同样**只发内参卡一张**，不叠加其他卡。

**线索入池「猎隼线索池」多维表格**（notify.json `bitable` 块驱动，已按真实字段校准）：

1. `judge.py --bitable` —— 把待写线索构建为 `out/bitable-pending.json` 预览（离线）。
   构建时会用**当前规则重算匹配**：旧规则遗留、现已不满足"中国企业+出海"硬筛的线索
   自动标记 filtered 排除；记录只填机器可靠字段（公司名称/业务描述/赛道/标签细分/
   融资轮次/资方/曝光媒体/GCP切入点/跟进状态/抓取时间/官网兜底链接）。
2. **AI 调研补全（入池硬前置，代码强制）**：按 `references/bitable-fields.md` 字段标准，
   用已有数据源（facts 档案/情报流水）+ 联网调研补齐 **14 个必研字段**（业务/融资/资方/
   经营规模/技术底座/CEO/规模/年限/城市/联系方式/官网/GCP切入点/破冰话术等），
   写 `log/enrichments.jsonl`（契约见该文档）；查不到填规定兜底值（未查明/未公开/
   未查询到有效信息），**不猜**——查不到≠可以不写，兜底值本身就是调研结论。
   审计：`judge.py --research-check`（未达标退出码 2，逐企业点名缺口）。
   **调研不齐全的线索 `--commit` 会被拒绝写入（exit 4，result=blocked）**——残缺画像
   会污染线索池、让破冰话术失真、让后续潜在线索判断失去依据。补齐后直接跑
   `judge.py --bitable --commit`（会重建预览吸收补全字段）。select 值写入前仍过选项校验。
3. `judge.py --bitable --commit` —— **自动入池（默认，无需人工确认预览）**：一条命令
   先重建预览吸收最新调研、再按「公司名称 + 别名候选」精确检索去重（任一命中即
   exists 跳过，防同公司异写重复建行），按最新 field-list 校验选项值后写入，
   结果回写 leads.jsonl 与 `log/bitable.jsonl`。重复执行幂等（exists 不重写）。
   输出带表格视图链接。人工**事后**在表内核查修正。
   （`--bitable` 单独跑仍可用于只看预览不写入。）
4. `judge.py --lead-card` —— **仅当用户明确要"看线索"时才跑**：重产最近一轮线索卡
   （私信 + 群卡两版，此版为准）：每条线索带「查看线索」按钮 record 级直达表格记录；
   exists（此前已入池）的标注「已存在」且**不进群卡**——群卡只含全新 P0。
   `--input` 阶段产出的线索卡/群卡是写入前快照，一律以本命令产出的最新时间戳版本为准。
   **默认不发**：入池成功后只汇报"已写入 N 条 + 表链接"，不主动发线索卡。

## 洁净验证标准 SOP（验证"新环境"效果时按此执行，勿即兴发挥）

每轮洁净验证都是新场景，历史上每轮都冒新问题的根因是**步骤即兴 + 问题只在落盘时暴露**。
标准顺序（2026-10-27 定稿，配套 `--dry-run` 预检）：

1. **备份**：`cp -r ~/.market-intel ~/.market-intel.bak-clean-<日期-时刻>`；
   删除更旧的备份（只留最新一份，它是复判源兼安全网）与工作区 `*.bak*` 残留。
2. **清基线**（用命令，**不要手敲 rm**）：
   ```bash
   python3 pipeline.py --clean            # 演练：只打印将删/将留，不动手
   python3 pipeline.py --clean --yes      # 确认后真删
   ```
   **保留清单驱动**（`pipeline.CLEAN_KEEP`）——工作区只该有三类东西：
   - **环境身份**：`sources/rules/notify/entities/denylist`（删了要重配）
   - **业务记忆**：`facts/`、`log/leads.jsonl`、`log/enrichments.jsonl`
     （删了会重复入池、重复调研、丢线索）
   - **素材缓存**：`state/hero_images.json`（重建需重传飞书，代价高）
   其余**一律清掉**：`state/streams`（差分基线）、`state/digest_anchor.json`、
   `state/pending.json`、`state/health.json`（源健康账簿，继承旧 down 会误判）、
   `out/`、`log/intel.jsonl`/`discarded`/`rolled_out`/`runs`/`bitable`/`unjudged`。
   **为什么用保留清单而不是删除清单**：早期列举要删的，结果新增的运行时文件
   （如 `state/health.json`）被静默漏删；改列举要留的，未来新产物自动被清。
   **为什么必须用命令而非手敲 rm**：历史上手工 rm 漏删过 `log/intel.jsonl`
   （增量差分失效、历史情报全部重判）、也多删过配置；命令带演练模式。
3. **全量首扫**：`pipeline.py --run`（16 源实测 **230±10 条**——滚动源每轮内容会变，
   具体条数不必对齐，看的是"没有 baseline 静默跳过、归档旧文被收口"两个行为；冷启动时
   归档型源按 30 天窗口收口，无时间戳条目全部保留，见陷阱 56）。
4. **构建判定（零幻觉复判）**：按 change_id 从备份 `log/intel.jsonl`/`log/discarded.jsonl`
   原样复用历史判定（含 merged_change_ids 的主条记录要整个拷回——被合并条目换源
   重现时靠它防重发），**只逐条判定真新增**；url/名称一律从 latest.json 带回。
5. **沙箱预检（必做）**：`judge.py --input judged.json --already-sent <备份>/log/intel.jsonl
   --dry-run` —— 临时副本上完整演练（白名单/覆盖度/grounding/sent-guard/产卡），
   真实工作区零写入；**预检通过才进行下一步**，失败按报错修正后重跑预检。
   🔴 CHECKPOINT：预检未通过禁止进入第 6 步。
6. **正式落盘**：同命令去掉 `--dry-run`；核对输出与预检一致。
7. **AI 内容核查 + 发通知（只发内参卡一张）**（目标以 `notify.json` 为唯一配置源）：
   `--digest` 产内参卡 → **先做「AI 内容核查」五项**（旧闻/判定质量/空段骨架/数字/版式，
   见工作流第 7 步）→ 有问题的就地修正数据重产卡 → **再发本人私信预览** →
   确认后才按 `notify.chat_id` 发群；**发送成功后** `--digest --commit` 推进锚点
   （失败不 commit）。
   **默认不发情报卡/线索卡/群@/状态卡**——除非用户明确点名（见「发送纪律」总则）；
   有 high 情报时内容随内参卡「行业重点新闻」段带出，不额外发情报卡。
   **重置后首跑 digest 是 anchor=None 的全量窗，发送前必须核对卡内不含
   已通报旧闻**（应全被 suppressed_by_guard 过滤；leads 段允许带"此前已
   登记"标注的历史线索）。
   🛑 STOP：发送前核对 = **AI 内容核查通过 + 本人私信确认**双闸（飞书卡片在会话内
   无法保真渲染，实卡以私信为准）；任一不通过则不发群、不推锚。
   **测试期红线**：用户明令只发本人时，所有卡一律只发私信、不发任何群；发送后
   用 `chat-messages-list` 核验目标群本轮 0 条消息。
   **入池边界**：线索入池（`--bitable --commit`）不在本步、不受预览断点约束，
   见第 5 步；入池后默认不发线索卡。
8. **体积与分片检查（v0.6.6 补，发送前必做）**：确认每张卡
   `json.dumps(card, separators=(",",":"))` **≤ 30KB** 且**元素 ≤ 200**
   （飞书硬上限；超出报 `230099/11310 element exceeds the limit` 或 `230025`）。
   `write_card` 已内置护栏并自动分片，看到 `[card-size] ... 已切成 N 张`
   就**必须把 N 张全部发完**——只发第一片 = 丢掉后面所有内容，
   且锚点随后推进 → 永久丢失。分片文件按 `-p1/-p2` 排序即为发送顺序。
9. **真增量轮验证（必做，2026-10-27 补）**：完整跑完一轮后**不清基线**再跑一次
   `pipeline.py --run`，核对：`removed` 应为 0（定长窗口源的消失只会是挤出）、
   新增条数为个位数。这是唯一能测到 removed 路径的步骤——历史上十九轮洁净验证
   （全部清基线走全量首扫）都没覆盖，导致陷阱 39 潜伏到首次真增量才暴露。
10. **收尾**：删临时 judged.json；教训若为新坑，代码化或入陷阱清单后再结束
   （"预检拦住的问题"也要评估是否值得代码化——复用场景的坑一律代码化）。

## 已知边界与陷阱（一期实测）

1. **中文媒体原生 RSS 大多已死**：36氪/机器之心等传统 RSS 地址实测返回 HTML（2026-10-23）。
   已验证可用：量子位、雷峰网、极客公园、TechCrunch。其余走自部署 RSSHub（公共实例
   rsshub.app 被 Cloudflare 拦截，不可依赖）。
2. **公众号（mp_account）必须低频**：依赖搜狗通道，时灵时不灵；建议 ≥120 分钟轮询、
   `windowed: true`；解析到 0 条脚本会显式报错（按源失败处理），不会静默空结果。
   不要把它当唯一信源。
3. **RSS 键规则**：链接唯一用链接；多条共用链接用 Atom id/guid（change-watch 陷阱19 的移植）。
   给新源配 RSS 前先看条目是否共用链接。
4. **web_page 监测有两种模式**（`config.mode`）：`keywords`（默认，招聘页：关键词出现/消失，
   粒度是关键词不是岗位条目，改关键词后需重建该源基线）；`links`（资讯列表页/榜单页：
   提取文章链接差分，新出现链接=added，天然实现"排除霸榜只看新晋"的榜单语义）。
   换模式或改 `link_pattern` 后需重建该源基线（删 `state/streams/<source_id>.json` 重跑 --baseline）。
5. **融资金额是近似值**：`parse_amount_cny` 只用于门槛比较（美元按近似汇率 7.2 折算，
   模糊表述"数千万"按 1000 万下限）。卡片与档案保留原文 `amount_text`，不要拿近似值对外引用。
   英文写法（`$30B` / `$200M` / `$1.5billion`）已支持（实测 TechCrunch 源首次运行曾因
   只认中文单位导致大额融资线索漏报）；无美元符号的 bare "35million" 不折算汇率。
6. **judge.py 幂等**：按 change_id 去重，同一 judged.json 修复后重跑不会重复落盘 intel/
   discarded（实测发现修复前重跑会双写，已修复并加回归测试）。但**卡片会重新生成**——
   重跑后以最新时间戳的卡为准发送，旧卡作废。
7. **规则匹配的是企业档案，不是原始事件**：同一公司在多渠道的事件会聚合到同一档案；
   这正是 `within_days` 类条件能成立的原因。公司识别靠词表 aliases + 域名，认不出进
   `unknown:*` 档案待归并——定期归并 unknown 档案并充实词表。
8. **unknown 档案的悬置**：`unknown:*` 企业不参与通知（匹配可以命中但 AI 应在判断阶段
   尽量给出可归一的公司名）；词表里补上别名后档案自动归并。
9. **「JS 渲染抓不到」先复核再下结论**：AI产品榜（aicpb.com）2026-10-23 曾判"前端渲染
   抓不到"而禁用，10-26 复核发现实为 Nuxt SSR、links 模式可正常解析各分榜头名（21 条）——
   误判原因未用带 UA 的完整请求验证。AppMagic 则实测确认纯 SPA（仅 cookie 横幅），
   登记停用留档；列表页类源（智东西/品牌方舟/投资界/活动行）links 模式实测可用。
10. **活动行时间/地点靠详情页富化**：活动行 RSS feed 只有标题+链接（description 为空）。
   源配 `config.detail_enrich: true` 后，管线对新增条目自动抓活动详情页解析内嵌
   `ativityJson`（站点源码就少拼一个 c），把时间/地点/主办方/报名规模写进变更 summary；
   解析失败静默保留原条目（AI 才可写「见报名页」并注明）。单轮抓取上限
   `settings.detail_enrich_max_per_round`（默认 12）。
11. **调研 entity_id 必须与线索 entity_id 完全一致**：调研补全写 `log/enrichments.jsonl` 时
   `entity_id` 要用 facts/leads 里的原值（如 `unknown:文远知行`、`moonshot`），自造 ID 会导致
   调研静默匹配不上、入池记录字段全空。管线已加双保险：entity_id 匹配不上时按 entity_name
   兜底（stderr 提示修正），完全未被消费的调研会告警点名。调研前先
   `grep entity_id log/leads.jsonl` 确认原值。
12. **P0/P1 分级口径**（需求文档）：P0 = 近1月融资 / 近3月业务暴增 / 发布新产品 /
    榜单新晋，任一命中即 P0（市场优先建联，实时通知）；仅满足画像（半年内融资、
    出海相关招聘）为 P1（入池+日报）。`notify_p1: false` 时 P1 不实时推送。
13. **grounding 对"B2B"类字母数字缩写会误报**：说明文字里的 B2B、T1 等缩写中的数字
    会被当成数字核对（实测 2026-10-23），只告警不阻断；在 `number_notes` 里申报
    （如 `{"2": "B2B 为缩写"}`）即可消除，二期可加缩写白名单。
14. **卡片 markdown 行内粗体：闭合 `**` 后必须跟空格**：`**时间：**值` 这种
    "全角标点收尾+紧贴正文"的写法不满足粗体判定，星号原样显示（实测 2026-10-23）；
    写成 `**时间：** 值` 即可。独占一行的 `**标题**` 不受影响。
15. **猎隼线索池字段要抄表内惯例**：技术底座查不到填"未查明"、联系方式填
    "未查询到有效信息"、企业规模/成立年限/城市填"未公开"——不空着、不猜、不造选项；
    各字段定义与调研渠道见 `references/bitable-fields.md`（按 100 条历史记录反推校准）。
16. **调研完整度是入池硬门槛（2026-10-26 起）**：`fields` 必须 14 必研字段齐全
    （缺兜底值也算缺），`--commit` 对未齐全线索拒绝写入（exit 4，bitable.jsonl
    result=blocked）；`--research-check` 逐企业审计。存量教训：早期契约只要求 8 个
    字段、且"可省略"，导致 11 家已入池企业缺融资动态/经营规模/官网等——残缺画像
    让破冰话术失真、后续判断失据（Homeika GMV 还写错口径），已全部真实联网回补。
    经营数据必须注来源口径，多口径冲突取可溯源者并在 notes 记录纠错。
17. **情报卡族视觉差异纪律**：market-intel 情报卡统一**紫色系**（violet 头 +
    `report_outlined` 图标 + violet-50/100 描边块），与 change-watch 蓝色铃铛监控卡
    一眼区分（2026-10-23 实测）。语义色共用不改：红=强提醒/P0、
    绿=正常/P1、黄=异常。改样式必须先发 notify.json 配置的目标群实测渲染，
    本人确认后再扩大发送。
18. **lark-cli base batch 响应结构是 `data.record_id_list`**（2026-10-26 实测）：
    `+record-batch-create/update` 成功响应不含 `records[].record_id`，直接解析会
    永远拿不到、每次新建都白白多跑一次检索（曾误判为"响应未含 record_id"）。
    用 `bitable._extract_new_rid()` 解析（兼容两种结构）。同理注意：`+record-delete`
    的 --json 要 `record_id_list` 键；`+record-search` 响应数据在 `data.data` 矩阵 +
    `record_id_list`（没有 `items` 键，人工验证时别读错）。
19. **exists 线索的通知语义必须分层（2026-10-26）**：已在线索池的公司（写入层
    `bitable_status=exists` 回写）不是新潜在线索——私信卡中性标注「已存在·已在线索池」
    （violet 块），**绝不进群 @ 催建联**（群卡只收全新 P0，`lead_card_split` 分流）。
    去重检索用主名 + 档案别名候选（`_dedupe_candidates`，上限 4 次），防同公司异写
    （如「月之暗面」vs「月之暗面科技有限公司」）重复建行；写入 failed 的线索保留
    待写状态下轮自动重试（终态仅 pushed/exists/filtered），一次网络抖动=静默丢单
    是踩过的坑。线索卡/群卡一律以 `--lead-card`（commit 后）产出的最新版为准发送。
20. **judged.json 顶层 `discarded` 键会被自动并入（2026-10-26 起，代码层兜底）**：
    构建判断文件时把弃权条目单独放 `{"discarded": [...]}` 而忘并入 `intel` 列表，
    会让覆盖度校验报缺失、退出码 2（实战踩坑两次）。现已由 `absorb_discards()`
    自动吸收并在 stderr 提示——构建脚本可直接只填 `intel`，不必手工合并。
21. **洁净重置流程（验证"新环境"效果时）**：先整目录备份（`cp -r` 工作区到
    `*.bak-clean-<日期>`）→ 再清 `state/streams/`、`state/digest_anchor.json`、
    `out/` 旧卡，保留 `rules/sources/notify` 配置与 `leads/enrichments/bitable`
    业务记忆（防重复入池）。**`log/intel.jsonl` 是「已发登记」**：清空它会让全部
    历史情报重新通知轰炸——重置后重判时用 `judge.py --input judged.json
    --already-sent <备份>/log/intel.jsonl`，命中的已发情报由代码强制
    `notify=false`（`demote_already_sent`，无需人工逐条标注）。差分基线清零后
    首轮即为全量首扫（14 源实测 244 条）。**复用旧登记记录进 judged 时**（按
    change_id 映射原样拷回历史判定，是零幻觉复判的推荐做法），记录会带落盘
    回写字段（logged_at/grounding/grounding_notes）——`strip_writeback()` 已
    代码层自动剥离（stderr 提示）；弃权登记是 `{change_id, reason}` 结构，与
    judged 契约不同，`strip_writeback()` 同步归一为 `{discard, discard_reason}`；
    其余未知字段仍被白名单点名拦截，属拼写错误防护，勿绕过。
    **组装常见笔误（2026-10-27 实测）**：构建了 `discarded` 列表却忘放进
    输出 dict 顶层——覆盖度校验会点名全部弃权 change_id，按报错把键补回
    `{"intel":…, "discarded":…, "facts":…}` 即可；dry-run 先行时此错误
    零污染拦截。另注意 macOS 自带 grep 是 BSD 版，`\|` 交替不生效，
    多模式排查用 `grep -E "a|b"`，勿凭 0 命中下「记录缺失」结论。
    **复判流程整体见「洁净验证标准 SOP」，配合 `--dry-run` 预检执行。**
22. **调研与修正必须用表内选项精确值（2026-10-26 实测）**：写 `所在城市/区域`、
    `成立年限`、`企业规模` 前**先拉 `+field-list` 核对选项**——「上海（徐汇区）」

38. **下载临时文件必须放 `/tmp`，不能用系统默认临时目录（2026-10-27 实测）**：

    文件会被 `lark-cli` 拒绝读取（`cannot open file`，与权限位无关，chmod 644
    也无效）；`/tmp` 下同一文件正常上传。头图 URL 下载、媒体中转一律

39. **增量轮次 `removed` 噪音双根因（2026-10-27 实测，v0.4.9 代码化）**：首次
    真实增量轮（有 prev 快照）一次冒出 167 条变更，其中大量是本轮滚出窗口的
    旧闻被当成「真的消失」。两个叠加根因，**全量首扫轮永远不暴露**（无 prev
    快照、不产 removed），故潜伏至首次真增量才炸：
    - **① `parse_iso` 只认 ISO 8601**：RSS 的 `published` 原生格式是 RFC 2822
      （`Mon, 26 Oct 2026 18:11:43 GMT`）→ 解析成 None → windowed 滚动的
      时间比较恒不成立。已修：RFC 2822 回退（`email.utils.parsedate_to_datetime`，
      标准库零依赖）。**教训**：凡比较时间戳的地方都要先验解析率，
      `[parse_iso(x) for x in items]` 里 None 占比 >0 即为静默失效。
    - **② 滚动判定条件本身错**：旧实现 `shrink = bool(added) or len(cur)<len(prev)`，
      把「有新增」当收缩信号；更关键的是要求 `pub < oldest_cur`，而**定长窗口源
      的消失条目是被等量新条目挤出**（10 进 10 出），pub 天然晚于当前最旧条目，
      条件永不成立。已修：**满窗（`len(cur)>=len(prev)`）= 必然挤出 → 全判 rolled**；
      只有真收缩（源变少）才按时戳保守判 removed。
    - **实测对照**：修复前 167 条（含 17+ removed 噪音）→ 修 parse_iso 后 40 条
      → 再修滚动判定后 **24 条全 added、removed 归零**，连续第二轮仅 5 条真新增。
    - **验证纪律**：洁净验证轮必须包含**至少一次真增量轮**（不清基线、有 prev 快照），
      否则永远测不到 removed 路径——这是十九轮洁净验证都没覆盖的盲区。
40. **「发送纪律」必须区分业务动作与展示动作（2026-10-27 用户纠正）**：曾把
    「用户触发先预览确认」写成一条笼统的总纪律，同时又在下方保留「线索闭环不受
    本纪律约束」豁免条款——两条互相矛盾，AI 读哪条都合理，行为必然飘移。更危险的是
    笼统写法会让 AI 把**入池写入**（`--bitable --commit`）也当成"发送类动作"卡住确认，
    **直接压住线索、丢单**。正解是**按动作性质分类**，不按"是不是用户触发"分类：
    - **业务动作**（入池写入）：特批豁免，命中即写、去重不建重复行、写完给链接、
      人工事后核查——卡住即丢单，宁快勿慢。
    - **展示动作**（一切发卡）：默认**只发内参卡一张**，情报卡/线索卡/群@/状态卡
      除非用户明确点名一律不发——发多了就是消息轰炸，宁慢勿滥。
    - 两者**不得混用**：入池成功 ≠ 要发线索卡；卡要预览确认 ≠ 入池也要确认。
    判断口诀：**写入看"会不会丢单"（快），发卡看"会不会轰炸"（稳）**。
41. **锚点推进必须同步补「已通报」标记（2026-10-27 实测缺口，v0.5.0 代码化）**：
    旧 `_advance_anchor` 只改 `digest_anchor.json`，**不给刚发出的记录打
    `suppressed_by_guard`**——这些记录永远留着 `notify=true` 且无标记。平时无害
    （锚点之后才进 digest 窗口），但**锚点一旦重置/回滚，它们会以旧闻身份
    重新推送到内参卡**。实测发现 6 条历史情报正是此状态（`logged_at` 早于锚点、
    notify 仍为 true、无标记），靠人工核查才补上。已修：`_advance_anchor(...,
    mark_sent=True)` 在推进锚点的同一动作里，把窗口内（旧锚点之后、now 之前）
    的记录统一补标并压 `notify=false`——**"锚点覆盖"与"已通报契约"从此原子一致**，
    不再依赖人工记得传 `--already-sent`。
    **排查方法**：`notify=true 且无 suppressed_by_guard 且 logged_at <= 当前锚点`
    → 即为漏标（已发过但没打标记），需补标后重推锚点。
    **边界修正（v0.5.2）**：补标条件必须用 `ts >= anchor_ts` 而非 `>`——锚点语义是
    「已覆盖到的时刻」，落在锚点上的记录同样属于本期已发；用严格大于会永久漏标
    （实测 6 条记录 logged_at 恰等于锚点，正是此边界）。
42. **已落盘记录重判时的漏发（2026-10-27 实测漏发，v0.5.2 修复）**：`cmd_input`
    落盘循环里 `if change_id in seen_intel: continue` 会跳过已存在记录——但
    **上轮落盘 notify=true 却未发出**（锚点未推进）的记录，本轮重判仍为 notify=true
    时也被这个 `continue` 吞掉，进不了 `notified_intel` → **卡片里没有它 → 永久漏发**。
    修复：已存在且本次判定 notify=true 的记录，从磁盘取原 logged_at 后同样加入
    `notified_intel`（不重复落盘，但必须进卡）。
    **判断"到底该不该发"的唯一依据是"有没有随内参发出过"**，不是"是否在登记里"：
    - 发了但没打标 → 补 `suppressed_by_guard`（陷阱 41）
    - 没发（`logged_at >= 锚点` 或 `notify=true` 且晚于 `--sent-before`）→ 必须进卡
    **实操提醒**：无法确定某条是否发过时，查锚点与 `logged_at` 比较，别凭"登记里有"
    就判已发——那正是本次误判的根源（曾误把已发的 2 条当未发、又把未发的当已发）。
    **性能附注（v0.5.3）**：该分支取原 `logged_at` 时，早期实现是在循环里
    `read_jsonl` 全量读文件找同 id（O(n²)，实测单次 3.7ms × 记录数）；已改为
    循环外一次性建 `existing_logged_at` 索引。**凡循环内读文件都要先建索引**。
43. **页面监测 links 模式的 `removed` 是正确语义，不是 bug（2026-10-27 审查结论）**：
    `_page_links` 产出的 `published` 恒为 `None`（锚文本里没有可靠时间），且这类源
    配 `windowed: false` → 首页文章被换掉时必然判 `removed`。审查时曾疑为缺陷，
    **二次论证后确认不改**：① 语义正确（文章确实从首页消失了）；② 规模极小
    （实测 143 条弃权里仅 6 条属此类）；③ 改判定语义会动到差分层核心逻辑，
    风险远大于收益。**处理方式**：判定阶段统一按"页面监测文章下架（旧闻，无情报
    价值）"弃权留痕即可，不必特殊代码路径。
    **通用纪律**：审查发现"看起来像 bug"的行为，先问三件事——语义对不对？
    规模有多大？改动风险 vs 收益？三者不成立就不要改，避免"为改而改"引入新问题。
44. **判定从严：`significance: low` 一律 `notify: false`（2026-10-27 实测判定过松）**：
    实测把一条"某公司研报/分析师强 call"类条目判成 `low` 却给了 `notify: true`，
    结果它进了内参卡「行业重点新闻」段（该段按 significance 排序取前 N，**不过滤 low**）
    ——读者看到的是研报套话标题，价值低且拉低卡面质量。
    **纪律**：
    - `low` = 边缘动态 → **必须 `notify: false`**，只作归档留痕，不进卡；
    - 无具体企业名/无具体事件的研报、观点稿 → 直接 `discard` 或 `low` 不通知；
    - **注意 `_news_elements` 不过滤 low**，卡面质量完全依赖判定阶段把关——
      判定放水 = 卡面被噪音污染，这个责任在 AI 判定侧，不在渲染侧。
    **已发出的处置**：内容已随卡发出无法撤回，保留 `notify=false + suppressed=true`
    的已发事实，在 `notify_reason` 里注明"判定偏松、后续从严"，不篡改已发历史。

45. **`highlight` 不得自带「看点：」前缀（2026-10-27 实测，18 条数据受污染）**：

46. **预览前必须做 AI 内容核查（2026-10-27 用户明令，五项硬门槛）**：产卡后不能直接

47. **新闻段 `limit` 必须豁免 `notify=true`，否则永久漏发（2026-10-27 实测，最严重的一类）**：

    陷阱 39 把窗口滚动判定改成「满窗即挤出，收缩才判 removed」，但 `shrink` 用的是
    `len(cur) < len(prev)` **绝对比较**——活动行列表页条数在 20/21 之间随机抖动

    三处共同后果相同：锚点一推进，`logged_at` 早于新锚点 → **判定成功但永久漏发**。
    **通用纪律（本坑的元教训）**：文档里写"统一口径"时，必须同轮用
    `grep -n "limit=" scripts/*.py` 把每一处逐个标注"数据源是否含 notify=true"，
    并**造 `[notify=True] × N>limit` 的实测**（不是看代码像不像）。
    **"我在文档里写了"不等于"代码里做了"**——这是陷阱 48 的第三次同型复发，
    说明"改一处就收工"是结构性惯性，只能靠机械扫查+实测阻断。
61. **活动情报缺 `activity` 明细会两头落空（2026-10-27 实测，v0.6.5，漏发类）**：
    内参卡活动段按 `x.get("activity")` 取数，新闻段按 `type != "活动情报"` 排除 ——
    当 AI 漏填 activity（或详情页富化失败导致 AI 无处取值）时，这条记录被**两段
    同时抛弃**，`briefing_card` 甚至因全空返回 `None`（不产卡）→ 永久漏发。
    **已修**：缺 activity 明细的 `活动情报` 降级进新闻段按普通情报渲染
    （有 title/summary 就能显示），并 stderr 提示回判据补全。
    **判断口径**：activity 是**排版增益**（进日历段、带时间地点），不是内容本身。
    内容完整性由 title 保证；缺明细属排版瑕疵，不该让内容消失。
    **通用纪律**：多段落卡片里，凡"某段按 A 条件取数、另一段按 `not A` 排除"的
    筛选结构，都要检查**A 条件不满足但落进排除区的记录**去哪里了——
    这是"互补筛选"的经典盲区（`if X: 段1 elif 排除条件: 跳过` 漏掉了 `X 为假` 的分支）。
62. **判定必须按 `change_id` 索引，绝不能用「列表序号」（2026-10-27 实测，v0.6.5，最隐蔽的一类）**：
    本轮真实触发时踩到：先用「序号 → change_id」映射做判定，随后因清理重跑，
    **两次采集的条目集合不同**（RSS 滚动源每轮内容会变），序号对应的内容全变 →
    237 条判定的 `summary` 大面积张冠李戴（标题对得上、摘要全错位）。
    **它差点没被发现**：`title` 是从原文带回来的所以完全正确、覆盖度校验也过
    （change_id 都回答了）、字段白名单也过——只有 **grounding 校验**因为"说明里的
    数字在原文里找不到"才暴露出来（如把「淘宝砸 1.2 亿」的摘要配到了 Meta 融资那条）。
    **正确做法**：判定直接以 `change_id` 为键（`add("d7184f96bb82", ...)` 形态），
    脚本对每个 id 断言"必须在本轮窗口内"，不在即报错退出；末尾断言
    "窗口内所有 change_id 都已覆盖"。**不要先生成序号映射再用序号查**。
    **通用纪律**：凡"用位置索引关联两份数据"的地方，先问一句
    **两份数据的顺序/成员会不会变**——滚动源、分页接口、并行采集都会变。
    稳定键（content-addressed id）才是唯一安全索引；序号只适合"同一份数据内部"遍历。
    另注：grounding 不只是"防 AI 编数字"，它同时是**判定与原文对账的最后防线**，
    永远不要为了让告警闭嘴而放宽它。
63. **列表页锚文本自带序号，会污染标题（2026-10-27 实测，v0.6.5，显示缺陷类）**：
    品牌方舟等列表页的锚文本是「5. AI软硬件公司「Ambi」完成1.74亿元Pre-A轮融资」——
    「5.」是**页面列表序号**。`parse_web_page` 的 links 模式直接取锚文本当 title，
    于是卡片新闻段渲染成「15. 5. AI软硬件公司…」**双重编号**，读者会以为漏了 1-14 条。
    已修：`collect._strip_list_ordinal()` 只剥开头的「1~2 位数字 + 点/顿号 + 紧跟中文或字母」，
    实测不误伤 `3D 打印` / `5G 芯片` / `100 天` / `2026 卫星大会`（这些数字后跟的是
    数字或单位，不是点号分隔）。
    **通用纪律**：凡是"抓页面文本当标题"的地方，都要检查**页面自身的排版残留**
    （序号、栏目前缀、「置顶」「热」标签）——它们在页面里是导航元素，进卡片就成了噪音。
64. **修「漏发」时只顾内容、忘了体积，反而造成更彻底的漏发（2026-10-27 实测，v0.6.6，本技能自己的回归）**：
    v0.6.5 把 notify=true 从「按 limit 截断」改成「全部展示」——方向完全正确（陷阱 47/60 的
    结论），但**没有同时检查体积**，结果真实内参卡膨胀到 **39599 字节 / 178 元素**，
    **双双超过飞书硬上限**（请求体 30KB → 错误码 230025；元素 200 个 → 300305），
    发送**必然失败**。而且失败点在 `--digest --commit` **之后**（该命令先产卡、后推锚），
    内容已被标 `suppressed_by_guard` → **永久丢失**。
    **比原来的截断更糟**：截断至少把前 5 条发出去了，这个是整张卡发不出去。
    **已修（v0.6.6）**：`write_card` 成为唯一出口并内置 `split_card()`——
    超限自动按顶层元素切分、每片独立校验收紧、标题加 `（1/N）`、stderr 明确提示
    "全部都要发送"；同时 `--digest` 落 `state/digest_pending_send.json` 待发送清单。
    **为什么只能分片不能砍内容**：实测该轮销售指引只占体积 23%，**全删仍有 30KB**，
    内容量本身决定了单卡装不下；而销售指引是用户明令必填，砍它就是违令。
    **通用纪律（这是本轮最重要的方法论）**：
    ① **"不截断"和"不超限"是一对矛盾**，做前者时必须立刻量后者——
       凡是调整"展示多少条"的地方，都要同轮算一次**序列化后的字节数**；
    ② **量体积要用飞书实际发送的形态**（`json.dumps(separators=(",",":"))`）而不是
       文件大小——pretty 打印 52KB vs compact 39.6KB，差 25%；
    ③ **有硬上限的外部接口必须有护栏**，且护栏要放在**唯一出口**（这里是 `write_card`），
       散在各处必然漏一个；
    ④ **失败要留下可核对的凭据**：`--digest --commit` 一步做完"产卡+推锚"，
       中间没有"发送成功"的确认点，一旦失败内容就永久消失。落待发送清单是最低成本的对冲。
65. **"修一处收工"的第四次复发：这次是外部约束（2026-10-27，与陷阱 48/60 同型）**：
    陷阱 48 说"同类问题要一次查遍所有兄弟位置"，陷阱 60 说"文档写统一口径必须同轮 grep 实测"——
    本轮仍然在**换了个维度**（从"截断"换到"体积"）之后重犯：改完渲染数量就收工，
    没检查"这么多内容发得出去吗"。
    **共性**：每次改了"数量/频率/条数"这类量纲，都会引入一个**新的、没被检查过的约束面**。
    **可执行的检查清单**（改数量类参数后必跑）：
      - 字节数：`json.dumps(card, separators=(",",":"))` ≤ 30KB？
      - 元素数：发出 200 个上限了吗？
      - 条数：单条消息里有几十个按钮/链接，接收端会不会折叠？
      - 频次：分片后一轮发 N 条消息，是否触发飞书限频（单用户 5 QPS）或构成轰炸？
    这四项与"内容是否漏发"是**正交**的，只盯漏发必然在某一项上翻车。

66. **「同一事件多家报道」的合并契约写在文档里，但执行完全靠人记（2026-10-27 用户实测反馈）**：
    用户原话：「很多信息实际是重复的，虽然标题和文案有些不一样，但是实际表达内容是一致的，
    AI 协助和兜底就能很好的处理，为什么还会重？」
    实测一轮：**DeepSeek 出现 4 条、Kimi 出现 3 条**，讲的是同一件事（专稿 + 早报转载 +
    评测稿 + 榜单稿），全被当独立条目推上卡。而 `intel-criteria.md` 早就写了
    「同一事件多家报道：合并成一条，`merged_change_ids` 列出被合并的 change_id，只通知一次」
    ——**契约有、执行没有**。这不是脚本 bug，是"文档里写了的纪律没人执行"这一类问题。
    **已加兜底** `auto_merge_duplicates()`：落盘前按「主体 + 事件类型」双维度判重并真的合并
    （从条 id 进 `merged_change_ids`、`sources` 合并去重、原标题存 `merged_titles`）。
    **判据迭代了四次才可用**（这段历程值得记住，不要凭直觉简化）：
      ① 整串特征重合度 → 早报把多事件塞一条标题，特征被稀释（实测重合度仅 0.36）→ 漏判；
      ② 锚点含型号词（gpt-6/k3.1/pro）→「Kimi 泄露」与「DeepSeek 斩杀 GPT-6」共有 gpt-6 → 误报；
      ③ 只比主体实体 →「Kimi 发布」vs「Kimi 泄露」主体都是 kimi → 误报；「Meta 被罚」vs「Meta 合作」同理；
      ④ **主体 + 事件类型双维度** → 正反例全过（这才是能区分"同一件事被多家报道"与
         "同一家公司发生两件不同的事"的判据）。
    另需剔除**轮次词**（pre-a/series a）——否则「Ambi 完成 Pre-A」与「橘猫宇宙完成 Pre-A」
    会因共有 pre-a 被误判重复。
    **通用纪律**：凡"同一实体可能有多种表述"的去重，都不能只比实体名——
    **实体 + 动作**才是事件的完整标识。只看实体会把"一公司的所有事"判成一件事。

67. **「折叠面板」不能解决 30KB，反而更占体积（2026-10-27 实测）**：
    直觉上折叠能把长卡片压小，实测相反：一组「markdown + button」平铺 440 字节，
    用 `collapsible_panel` 包裹后 **807 字节（+367）**——折叠只改变**视觉展开状态**，
    header/border/padding 等固定字段照旧计入 JSON 大小，元素数也一样计入 200 限制。
    所以「视觉太长」可以用折叠解决，「发不出去」必须靠**减少内容或合并条目**。
    **同理：`column_set` 做左右分栏也是变大的**（一组 +252 字节），
    它能省视觉行数（41 组省 41 行）但让体积从 38050 涨到 48341，会**加剧**超限。
    **通用纪律**：遇到"太大发不出去"，先分清要解决的是**视觉长度**还是**序列化体积**——
    这是两个独立维度，能解决前者的手段（折叠、分栏）往往让后者更糟。

## 可移植性

- 全部脚本只用 **Python 3 标准库**（零依赖）；
- 不写死安装位置（`os.path.dirname(os.path.abspath(__file__))` 反推），全目录无 `/Users/xxx` 绝对路径；
- 状态、配置、日志都在工作区，是普通文件；多工具共享就让 `--workspace` 指向同一目录。
