# 企业事实抽取准则（facts）

`judged.json` 的 `facts` 数组：把变更里出现的企业事实抽成结构化记录，由脚本并入企业档案。
事实是规则匹配的原料——**抽取质量直接决定线索质量**。

## 记录契约

```json
{
  "entity_name": "公司名（取原文写法）",
  "aliases": ["同一公司的其他称呼"],
  "industries": ["游戏 | 电商 | AI硬件 | 应用 | 具身智能 | 智能制造 | 短剧 | 互联网"],
  "origin": "CN | null（中国企业则写 CN）",
  "going_global": "true | 省略（有出海/跨境/全球化业务信号时写 true）",
  "profile": "一句话业务描述（可选，供卡片与猎隼线索池）",
  "opportunity": "最大机会点（可选：与 WebEye 业务的切入角度）",
  "event_type": "funding | hiring | other",
  "event": { "按类型见下" },
  "change_ids": ["支撑本事实的变更 id"],
  "confidence": "high | medium | low"
}
```

## 行业口径（需求文档八行业，词表 industries 同源）

游戏、电商、AI硬件、应用、具身智能、智能制造、短剧、互联网。

- AI 公司按主营形态标「应用」（软件/模型服务）或「AI硬件」；
- 天然出海的行业在词表/档案直接标「短剧出海」等（行业名含"出海"即通过出海硬筛）；
- 行业拿不准时选最贴近的一个，并在 confidence 降级——不要自由发挥新行业名。

## 客户硬筛（scope 会拦，但抽取时就要对齐）

潜在客户 = **中国企业 + 业务出海 + 八行业内 + 不在黑名单 + 轮次 ≤ B**。抽取事实时：

- **origin: "CN"** 的判据：公司主体在中国（城市/注册地）、融资以人民币计、原文明确"中国企业"；
  外企/海外公司**不要**写 origin（例如 OpenAI）——写了也过不了筛选，只会污染档案；
- **going_global: true** 的判据：原文提到出海、海外市场、跨境、全球化、国际版、多国运营；
  行业本身天然出海（短剧出海、跨境电商）也算。

### 黑名单与轮次（2026-10-27 用户明令；代码在 `match.check_denylist()` 硬拦截）

抽取前先自检，命中就别费劲写细节——写了也会被 `denylist.json` 丢掉：

- **超级巨头/独角兽**（字节、SHEIN、拼多多/Temu、阿里、腾讯、网易、米哈游、莉莉丝、
  月之暗面、DeepSeek、智谱、MiniMax、小米、华为…）→ 命中即丢，**不是我们要的客户**；
- **成熟出海服务商/友商**（声网、钛动、白鲸出海、赤子城、PingPong、连连、飞书深诺、
  店匠、Mobvista、AppsFlyer…）→ 是生态伙伴，不是买云的直客；
- **已上市 / C 轮及以上融资 / 战略融资 / 并购** → 丢。用户原话："严禁推荐已上市企业、
  C 轮及以上的大额融资企业"。

**目标客群只有天使轮 / Pre-A / A / B 轮的成长型出海团队**。完整名单与口径以
`<工作区>/denylist.json` 为准（用户可自行增删，**不要改本文档或代码**）。
抽取侧的正确姿势：**遇到巨头就直接不抽 facts**，让条目走 intel 的 discard 留痕；
硬写进 facts 会白跑一趟（facts 会落档案但线索被拦，档案里堆一堆永远不建联的巨头）。

> 注意 facts 档案本身会保留（用于事实溯源与「为什么没推这家」的事后审计），
> 被丢弃的只是**线索**。审计时看 `log/leads.jsonl` 有没有它，不是看 `facts/`。

## event 按类型

- **funding**：`{date, round, amount_text, investors, source_name, source_url}`
  - `date` **必须是 ISO 日期 `YYYY-MM-DD`（硬要求，2026-10-27 升级）**：
    规则引擎用 `within_days` 判「近 N 天融资」，**日期解析不出就无法证明"近期"，
    该事件一律按不满足时效处理、不命中**（保守不虚报——线索误报会让市场同事
    建联扑空，比漏报更伤信任）。
    - 原文只给"本月/上周"→ 换算成具体日期（当月/当周内某日），并在 `confidence` 降级；
    - 原文完全无时间 → `date` 留空并在 `confidence` 写 low，**不要写"去年"、
      "近期"、"不久前"等无法解析的表述**（写了等于该事件永远不命中时效规则）；
  - `amount_text` 保留**原文写法**（中文如"近亿元人民币"，外刊英文如"$30B"、"$200M"均支持）
    ——脚本会近似解析用于门槛比较，但档案里保留原文，不拿近似值当事实；
  - `round` 用通用写法：种子轮/天使轮/Pre-A轮/A轮/A+轮/Pre-B轮/B轮/C轮/战略投资/IPO 等
    ——规则引擎按轮次识别「种子~B轮」优先级（需求文档：种子~B 轮企业拿钱后 3~6 个月
    启动扩张、IT 预算最宽裕），写"新一轮"会导致轮次识别不到；
  - 只有传闻金额、或金额出现在标题党语境里 → confidence 降为 medium/low。
- **hiring**：`{keywords, page_url}`——通常由 web_page 源确定性直录，AI 只需在
  报道类内容提到"该公司大规模招聘/新官上任"时补充（`{detail}` 摘要即可，入 other_events）。
  关键词口径（需求文档）：出海、跨境、全球化、云成本等扩张型岗位信号优先。
- **other**：`{kind, detail, source_url}`——kind 取值决定是否参与 P0 规则匹配，约定：
  - `business_surge`：业务数据暴增（客户介绍类通稿：用户/收入/订单激增、大力投产销、
    签约大客户）——需求文档 P0 信号之一；
  - `product_launch`：发布新产品 / 主产品大版本更新——P0 信号之一；
  - `rank_new_entry`：海外软件榜单**新晋**（AI产品榜、AppMagic 等）——P0 信号之一；
    注意榜单语义是"排除长久霸榜、只看新上榜"，霸榜软件的变化不要标这个 kind；
  - `merger` / `partnership` / `policy` / `other`：暂不参与规则匹配的事实留痕。
  - `detail` 里写清楚数字与对象（会进证据链与卡片）。

## 防张冠李戴（铁律，沿用 AIHOT IDENTITY_LEXICON 的原则）

- **`entity_name` 必须在支撑该事实的变更原文里出现过**，不许凭常识推断"这肯定是某某公司的"；
- 集团与子公司要分清：文中说"阿里云"就写"阿里云"，不要归到"阿里巴巴"除非原文明说；
- 同一公司多个称呼时，`aliases` 填全（原文称呼 + 词表别名），帮助脚本归一；
- 词表里没有的公司：照写原文公司名（脚本会建 `unknown:*` 档案），**不要硬凑到词表里
  相近的名字上**——归并靠词表维护，不靠模型猜测。

## 与 intel 记录的分工

- 一条变更既值得看又含企业事实 → `intel` 和 `facts` 各一条，共享 `change_ids`；
- 一条变更只是线索原料（如融资快讯）不值得单独通知 → 只写 `facts`，不写 `intel`；
- 两者都没有 → `intel` 里写 `discard`。**三选一必须发生，不许留空。**


## v0.6.12：范围与事件日期的严格口径

- 档案明确非 CN 时，城市／人民币关键词不能覆盖；明确 going_global=false 时不进入出海潜客。
- 融资事件 date 必须为可解析的发生日期；不允许 extracted_at 替代，未来日期不算近期。
- product_launch／business_surge 等事件请在 event.date 填发生日期（ISO 日期或时间）；
  无法证实时仍可保存事实，但不命中有 within_days 的近期信号组，不自动降为 P1。
- rank_new_entry 表示首次观察到榜单新晋，可以使用 extracted_at；招聘 last_seen 是观察时间，
  保留既有语义，无法解析或在未来的观察时间不算有效近期证据。
- 既有事实不自动改写或补日期；不能从采集日期猜事件发生日期。
