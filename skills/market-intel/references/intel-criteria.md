# 行业情报判断准则（intel）

对 `out/latest.json` 变更集逐条判断。四问结构沿用 change-watch 的 criteria，口味换成市场情报。

## 一、四条必答问题

1. **是值得看的行业情报吗？** 不是（站点噪声、活动邀约、纯营销、与行业无关）→
   `"discard": true` + `discard_reason`。**什么都不写 = 漏判**，会被待判队列反复带回，
   超过 24 小时进 `log/unjudged.jsonl`。
   **"判不出来" ≠ "判为无关"**：材料不足写 `significance: "unknown"`，落盘但不通知。
2. **什么类型？** 两到六个汉字短语，可复用。参考表：

   | 类型 | 含义 |
   |---|---|
   | `融资事件` | 企业完成新一轮融资（同时给 facts 抽一条事实） |
   | `产品发布` | 行业内公司发布新产品/新版本 |
   | `人事变动` | 高管更替、关键人才流动 |
   | `并购合作` | 并购、战略投资、生态合作 |
   | `政策监管` | 影响行业的政策、监管、合规动态 |
   | `行业趋势` | 有数据支撑的趋势、报告结论 |
   | `活动情报` | B2B 出海相关活动（判断准则与 activity 明细契约见 `references/activities-criteria.md`） |
   | `榜单新晋` | 海外软件榜单新上榜/登顶（AI产品榜、AppMagic 等）——内参卡「榜单监控」段按
     type 含「榜单」取数，榜单类情报统一用这个 type；霸榜产品的名次波动不标 |
   | `其他` | 自拟更准确的名字 |

3. **多重要？** `high`：大额/头部企业融资、行业级政策、代际性产品；`normal`：常规融资与产品动态；
   `low`：边缘动态；`unknown`：判不出来（不通知）。
4. **要不要通知？** `notify: true/false` + 一句 `notify_reason`。

## 一·四、`榜单新晋` 必须调研出实质信息（2026-10-27 用户实地反馈，硬要求）

用户原话：「榜单监控的每个内容都很短，都是『xxxx。需人工核实公司主体与融资轮次后决定
是否建联。』，而且信息 AI 不都会调研补全的吗？」

**问题定性**：这是判定偷懒，不是数据不可得。`AI产品榜` 列表页只给产品名 + URL，
但**详情页是服务端渲染的，公开可读**，真实数据齐全。实测 4/4 全部可提取：

| 产品 | 榜单项 | 指标 | 月环比 | 名次 |
|---|---|---|---|---|
| BEEMO AI | 全球增速榜(App) | 1.54M App 月活 | +23.62% | 第 1 |
| vivago.ai | **出海增速榜(App)** | 4.60M App 月活 | +17.10% | 第 1 |
| Higgsfield | 图片生成榜(Website) | 27.97M 网站访问 | +10.60% | 第 1 |
| OpenClaw | AI龙虾榜(Website) | 4.78M 网站访问 | −39.27% | 第 1 |

`vivago.ai` 是**出海增速榜第 1 名**——正是我们的目标客群，却被一句套话掩盖了。

### 硬要求

`type=榜单新晋` 的记录，`summary` **必须包含详情页能查到的客观数据**，
按此结构写（缺哪项就跳过哪项，不要编）：

```
<产品>「<一句话定位>」在 AI产品榜·<榜单项> 以 <指标> 位列第 <N> 名，月环比 <±X%>。
<这张榜的含义：增速榜=正在起量 / 出海榜=目标客群 / 图片生成榜=品类>。
<若要建联：可查到的公司主体线索；查不到就明说「主体待核实」>。
```

- ✅ 正例：「vivago.ai 在 AI产品榜·出海增速榜(App) 以 4.60M App 月活位列第 1，月环比 +17.10%。
  出海增速榜上榜 = 海外用户正在快速起量，属目标客群画像。产品定位：AI 视频导演工具。」
- ❌ 反例（**禁止**）：「xxxx 出现在 AI 产品榜，属榜单新面孔。需人工核实公司主体与融资轮次后
  决定是否建联。」——这句话对每条榜单都成立，等于**没提供任何信息**。
  「需人工核实」不是调研，是把我该做的活推给读者。

### 怎么取数（实测可用，2026-10-27）

详情页 URL 就是变更集里的 `url`。页面是 Nuxt 服务端渲染，`curl` 直接可读：
1. 抓 HTML → 去掉 `<script>` / `<style>` → 剥标签 → 压空白，得到纯文本；
2. 正则提取四项：
   - 榜单项：`AI产品榜·(.+?)[（(](App|Website|Webstie)[）)]`
   - 指标：`以([\d.]+[MK]?)\s*(App 月活跃用户|Webstie 访问量|Website 访问量)`
   - 环比：`月环比.*?([-+]?\d+\.?\d*)%`
   - 名次：`位列第\s*(\d+)\s*名`
3. **取到的数字要在 `number_notes` 申报**（`{"4.60": "取自榜单详情页月活"}`），
   否则 grounding 会因"原文没有这个数字"而告警——详情页数据 AI 主动获取，属合法外源。

### 多个榜单产品时的取舍（用户明令：真超限时优先砍不重要的）

榜单段是本卡里**信息密度最低**的段落。当整卡逼近 30KB 时，**优先减少榜单条目数**，
而不是去压缩新闻文案或销售指引。减少顺序：
1. 先砍「长期在榜、指标下滑」的（如环比为负、非出海榜）；
2. 再砍「品类与八行业关系弱」的（如纯工具类图片生成）；
3. **「出海增速榜 / 海外增速榜」上榜的永远优先保留**——它直接证明是目标客群。

## 一·五、资讯双轨（2026-10-27 用户明令重写：只抓公开透明的硬事实）

**总原则**：只抓**公开可核实**的事实（官方公告、财报、定价页、监管文件、权威媒体）。
**明确不采集**（公开渠道根本拿不到，不要试图挖）：`内部算力配额`、`私下大客户折扣`、
`未公开的商务条款`、`非公开投放金额`。这些写进判定即扣分——**不现实的信号等于噪音**。

### 轨道 1：技术战报与竞对价格战（`type` 用 `技术战报`）

按四类盯，命中即 `high`（价格战类强制 `high`）：

| 类别 | 盯什么 |
|---|---|
| **Google 动态** | Gemini 新版本/能力代际、Vertex AI / BigQuery / GKE 重大 Feature Drop、新可用区（Region）GA 商用公告 |
| **国际大厂** | AWS、Azure、OpenAI、Anthropic 的新模型与产品更新 |
| **国内核心模型（重点盯防）** | DeepSeek、阿里通义千问（Qwen/百炼）、字节豆包（火山引擎）、MiniMax、月之暗面（Kimi）、智谱（GLM）**在出海市场的动作** |
| **价格战（最高优先级）** | 竞对宣布降价、下调 API Token 价格、发布极高性价比新模型 → **必须第一时间推送** |

**强制字段 `sales_playbook`（销售对标指引）——`技术战报` 类 notify=true 时必填**：
必须回答"**出海客户拿竞对低价来压价时，销售怎么用 Google 生态防守/反击**"。
写法要求（60–120 字，必须落到具体能力，不许空话）：
- 引用 Google 侧**具体抓手**：全球合规（数据驻留/认证）、低延迟骨干网络、
  多模态能力、BigQuery 数据分析、GKE 弹性算力、Vertex AI 托管能力；
- 给出**一句话话术**（销售可直接照读）；
- ❌ 反例："我们更稳定更安全"（空话，等于没给）；
- ✅ 正例见本文件末「sales_playbook 范例」。

### 轨道 2：出海战略风向标（`type` 用 `战略风向`）

**不要泛泛行业新闻**，只抓「格局变化与红利转移」：

| 抓什么 | 举例 |
|---|---|
| 区域增长爆发点 | 中东短剧爆发、拉美社交起量、日韩游戏榜单变动 |
| 应用商店政策重大变动 | Google Play / App Store 分成、上架、隐私政策变更 |
| 海外买量单价剧变 | Meta/Google/TikTok 广告 CPM/CPI 显著波动（公开报告口径） |
| 当地数据合规新规 | GDPR/DPDP/PDPL 等新规生效、执法案例 |

**强制字段 `sales_strategy`（销售战略建议）——`战略风向` 类 notify=true 时必填**：
必须直接回答两问（50–100 字）：
1. **这个变动意味着什么机会？**（谁受益/谁受损，一句话）
2. **本周团队该调头抓哪个行业客户、主推什么方案？**（必须具体到行业 + 方案名）
- ❌ 反例："值得关注"（没有行动指令，等于没给）；
- ✅ 正例见本文件末「sales_strategy 范例」。

### 字段落盘契约（脚本会校验）

```json
{
  "change_id": "...", "type": "技术战报", "significance": "high",
  "title": "...", "summary": "...", "notify": true,
  "sales_playbook": "竞对降价 XX% 后，客户会拿价格压我们。防守话术：……（引用 Google 合规/骨干网/多模态具体能力）"
}
```
```json
{
  "change_id": "...", "type": "战略风向", "significance": "high",
  "title": "...", "summary": "...", "notify": true,
  "sales_strategy": "中东短剧单季增长 XX% → 短剧出海客户带宽与多区域部署需求激增。本周重点抓中东短剧出海团队，主推多区域低延迟 + 数据驻留合规方案。"
}
```

**阈值纪律**：`type=技术战报` 且 `notify=true` 时缺 `sales_playbook` → 脚本报错退出（exit 2）；
`type=战略风向` 且 `notify=true` 时缺 `sales_strategy` → 同上。**不许留空、不许占位符。**

## 一·六、重点竞对与趋势关注（历史口径，仍生效）

以下信源条目按重点口径判断，命中即至少 `normal`、有实质影响升 `high`：

- **Gemini 竞对**：新模型更新/发布（版本号、能力代际、基准成绩）、价格变动
  （API 定价、免费额度调整）——模型/价格两类都要盯；
- **Google Cloud**：重大更新（新区域、大模型托管能力、价格策略、生态合作）；
- **WebEye 关注行业趋势**：游戏、电商、AI硬件、应用、具身智能、智能制造、短剧、互联网
  八行业的结构性变化（技术拐点、平台政策、出海市场变动）。

## 二、事实抽取（与 intel 判断同时做）

条目里若出现**企业事实**（融资、招聘、归属行业），在 `facts` 数组里加一条（契约见
`references/lead-criteria.md`），并把该条 `change_id` 写进 `facts[].change_ids`——
这就是这条变更的"结论"，覆盖度校验同样认可。

同一事件多家报道：合并成一条 intel，`merged_change_ids` 列出被合并的 change_id，
`sources` 列全并给中文名，只通知一次。

### 什么算「同一事件」（2026-10-27 用户实测反馈后明确）

用户原话：「很多信息实际是重复的，虽然标题和文案有些不一样，但是实际表达内容是一致的，
AI 协助和兜底就能很好的处理，为什么还会重？」—— 实测一轮里 DeepSeek 出现 4 条、
Kimi 出现 3 条，讲的是同一件事，全被当独立条目推了。**这是判定执行不到位，不是脚本问题。**

判重看**两个维度同时成立**，缺一不可：

| 维度 | 成立条件 | 反例（不算同一事件） |
|---|---|---|
| **主体相同** | 同一家公司/同一个产品 | 「欧洲 GMV 数据」vs「希音欧洲招聘」——都涉欧洲，但主体不同 |
| **事件相同** | 发布/降价/融资/泄露/罚款/合作/榜单…属于同一类动作 | 「Kimi 发布 K3.1」vs「Kimi K3.1 成本数据泄露」——主体同、事件不同 |

**典型必须合并的形态**（实测高频）：
- 专稿 + 早报转载：「DeepSeek 新模型上线，价格更低」+「iPhone Duo 交付；DeepSeek 新模型…｜极客早知道」
  → 合并到专稿，早报的 change_id 进 `merged_change_ids`；
- 多家媒体同日报道同一次融资/发布 → 合并，`sources` 列全；
- 同一事件的快讯 + 深度解读 → 合并到信息最全的那条。

**明确不合并**：同一公司同一天的两件不同的事（发布新品 + 被罚款）是两条独立情报。

> 兜底：`judge.py` 落盘时会**自动合并**（`auto_merge_duplicates()`，v0.6.7）——
> 用「主体 + 事件类型」双维度判重，把从条并进主条：`merged_change_ids` 记合并关系、
> `sources` 合并去重、原标题存 `merged_titles` 可溯源，然后才落盘产卡。
> 所以即使判定时漏了合并，卡片上也不会重复；**但你仍应主动合并**——脚本只按标题判断，
> 拿不到正文语义，复杂情况（如"同一事件的快讯+深度解读但标题完全不同"）它看不出来。
> 合并建议同时写入 `out/dup-suggestions.json`（含主条/从条 change_id），供人工复核。

## 三、防假条款（命中任一即 discard）

- 纯营销稿 / 品牌宣传，没有可验证事实；
- 传闻、二手转述，无原始出处；
- 招聘平台自己的软文（真实企业招聘动态不算——按 hiring 口径抽 facts）；
- 与八行业（游戏/电商/AI硬件/应用/具身智能/智能制造/短剧/互联网）无关的一般性内容；
- C 端生活娱乐活动（活动情报白名单/黑名单见 `references/activities-criteria.md`）；
- 同一事件的重复报道（引用已记录条目的 change_id）。

## 四、时间与溯源口径（沿用 change-watch）

- 各源时间戳不可跨源比较；判断"新不新"以本技能采集时刻为准；
- `title`/`summary` 里的公司名、数字必须能在该变更原文里找到——脚本会做数字核对，
  对不上标 `grounding: "unverified"` 并点名，看到就回原文改；
- **数字核对是三层判定**（实测教训：`$30B` 写成"300亿美元"曾被误拦）：
  ① 直引原文数字 → 通过；② 常见单位/汇率换算（×10 亿↔B、÷10000 万、×7.2 汇率等）
  → 脚本自动兜底通过，备注留档；③ 兜底认不出的 → 在 `number_notes` 里申报
  `{"数字": "换算依据"}` 后通过，同样留档。申报必须属实，留档供人工审计；
- `url` 必须能点开原文；拿不到就说明依据不足，判 `unknown`。

## 五、sales_playbook / sales_strategy 范例（照着写，别写空话）

### sales_playbook（技术战报 / 价格战专用，60–120 字）

> **场景**：某国内模型把 API 输出价下调 40%，客户拿这个价来砍我们。
>
> ✅ **合格写法**：
> 「竞对降价 40% 后客户必拿价格说事。防守三步：①算总成本不只看 token 单价——
> 我们的骨干网直连让跨区推理时延低 30%+，客户少做一次重试就抵掉差价；
> ②合规杠杆：出海客户在欧盟/中东要数据驻留，我们有本地 Region + 认证齐全，
> 竞对走第三方转售合规链路更长；③用 Vertex AI 托管能力把客户的模型运维成本
> 转成我们的服务费。话术：『单价贵一点，但你少两个合规风险 + 少一次跨区重试。』」
>
> ❌ **不合格**：「我们更稳定、更安全、服务更好」（无具体能力，销售无法照读）

### sales_strategy（战略风向专用，50–100 字）

> **场景**：中东短剧市场单季度增长 120%。
>
> ✅ **合格写法**：
> 「中东短剧暴涨 → 短剧出海客户要同时解决『多区域低延迟分发』和『当地内容合规』。
> 本周重点转抓**中东短剧出海团队**（尤其刚拿 A/B 轮、正在铺量的），
> 主推『多区域边缘节点 + 数据驻留合规』组合方案，切入点是他们买量起量后的首屏卡顿投诉。」
>
> ❌ **不合格**：「中东市场值得关注，建议加大投入」（没有行业标的、没有方案、没有动作）


## v0.6.12：确定性去重与语义去重的分工

程序只自动合并标题、摘要、类型、销售指引、活动明细一致且标题足够具体的记录；
来源合并，完整从条存 merged_records。主体和事件类型相同只构成候选，不能证明同一事件。
对不同标题但同一事实的报道，AI 核对产品／版本／发生时间后用 merged_change_ids 合并。
同公司不同产品、不同融资轮次或不同活动场次必须分别保留。

前文榜单超限取舍发生在判定阶段：删除通知项需明确改为归档或弃权并说明理由；
进入产卡的 notify=true 不静默截断，必要时仍分片。不要在发送前直接删卡片元素。
